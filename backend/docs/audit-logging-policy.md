# POT Audit Logging Policy (Proposal)

**Related GitHub issues:** #588 (policy), #447 (audit logging expansion), #606 (two-admin approval)  
**Status:** Proposed for Stuart / Product Owner review — not yet approved  
**Scope:** Audit-log event selection, sensitive-data exclusions, retention, access and integrity. This document does not implement backend changes.

## 1. Existing implementation and context

The current backend includes:

- `backend/src/models/audit_log.py`: `AuditLog` with `id`, `user_id` (required foreign key to `users.id`), `event_type`, free-text `details`, and UTC `timestamp`.
- `backend/src/services/authentication.py`: `log_audit_event(...)` creates an `AuditLog` entry and commits it.
- `backend/src/routers/user.py`: audit entries for user creation (`user_create`), user approval (`user_approve`) and pending-user rejection (`user_reject`). The current entries include email addresses in `details`.
- `backend/tests/test_audit_logging.py`: tests that user creation creates an audit record.
- `backend/src/routers/auth.py`: login, registration, verification and password-reset flows that are candidates for further audit logging under #447.
- `CONTRIBUTING.md`: instructs contributors to remove identifying personal information and secrets from comments or logs.

The model documentation describes audit records as append-only. **That describes the intended policy, not proof of database-level immutability or a configured retention mechanism.** The current `details` field is unstructured, so adding new events without a common convention could increase privacy risks.

## 2. Events to log

Record meaningful security and accountability events, including successful and unsuccessful attempts where practical. The baseline should be:

| Area | Proposed events | Minimum outcome/detail |
| --- | --- | --- |
| Authentication | Login success and failure | Event type; outcome; actor ID when known; UTC timestamp |
| Account lifecycle | Registration, email verification, password-reset request and completion | Event type; outcome; user ID when known; UTC timestamp |
| User management | Create, approve, reject, role change, deactivate and delete | Actor ID; target ID (where appropriate); action; outcome; UTC timestamp |
| Approval workflow (#606) | Sensitive change requested, approved/rejected, completed, and single-admin bypass | Actor/target references; request reference; decision/outcome; bypass indicator |
| Security-relevant denials | Unauthorised or rejected privileged actions | Event type; outcome; safe internal references only |

Routine page views, sensitive business payloads, high-volume diagnostic records and normal non-security operations should **not** be copied into the security audit log by default. Additional events should be justified by a specific use case and approved before implementation.

For #606, the approved role rules require a second admin for privileged user-management actions and explicit audit flagging of a valid single-admin bypass. The audit design should also support documenting the rejection of a self-approval or an attempt to remove the last admin, without exposing secrets.

## 3. Minimum record fields

Use the existing schema where feasible. The proposed content for an event is:

- **Actor:** stable internal `user_id` if an authenticated actor exists.
- **Type:** controlled `event_type` identifier, e.g. `role_change` or `login_failed`.
- **Timestamp:** UTC timestamp.
- **Details:** a **sanitised**, concise event description or bounded codes, with only the internal target/request reference and outcome needed for audit.

Avoid unvalidated, user-supplied or arbitrary free-text content.

**Unresolved schema constraints:** `AuditLog.user_id` is currently required and linked to `users.id`. Failed logins involving unknown accounts have no valid actor ID. Deleting a user may also conflict with keeping historical records that reference that user. The implementation design for those cases needs explicit agreement under #447/#606; do not invent an actor ID or change foreign-key behaviour without review.

## 4. Sensitive data and personal-information exclusions

**Do not record:**

- Plaintext passwords, password hashes, PINs or security answers.
- JWTs, access/refresh tokens, password-reset and email-verification tokens, session credentials or secret values.
- API keys, application secrets, `Authorization`/`Cookie` header values.
- Complete request/response bodies, login forms, reset/verification links, or error traces containing submitted secrets.
- Real farmer names, sensitive farm-owner datasets, private personal information or location-level data not necessary for auditing.
- Unredacted email addresses or names where stable internal IDs are sufficient.

Existing entries generated by user-management code contain email addresses in `details`. This policy recommends **migrating future events to minimised descriptions** and separately assessing how pre-existing entries will be handled. Do not silently rewrite historical audit records.

Avoid logging raw error messages or validation payloads that might echo client-submitted content. If additional context is necessary, use an explicitly reviewed allowlist of fields.

## 5. Retention and disposal (decision required)

**Proposed initial policy:** retain routine security audit events for **180 days** from their UTC timestamp, subject to explicit Stuart/Product Owner approval and confirmation of applicable legal, operational and privacy obligations. **The repository does not currently establish this as an approved period**, and it must not be presented as a regulatory requirement.

- Document the approved retention period and operational owner.
- Where feasible, make the setting configurable and record any change to it.
- Preserve relevant audit entries during an active security investigation or approved preservation hold.
- After retention expires, use a separately authorised, documented maintenance process to purge eligible entries; no normal user-facing feature may edit or delete them.
- Align backup lifecycle and access restrictions with the agreed policy; specify separately what retention of archived copies means.
- Audit the maintenance operation without exposing sensitive content.

**Pending decision:** confirm or replace the proposed 180-day period before implementing automatic purging.

## 6. Integrity, access and monitoring

- Treat audit records as **append-only during normal application operation**.
- Do not expose individual record edit/delete operations through ordinary API or user interfaces.
- Restrict audit access to specifically authorised staff on a need-to-know basis; **admin-only is the initial proposal**, pending confirmation of whether authorised supervisors should have read access.
- Protect access to underlying tables, application logs and backups with least-privilege roles.
- Any retention-based purge or incident-preservation operation must be separately controlled and documented.
- Review sensitive administrative actions and #606 bypass events as part of operational monitoring.
- Audit activity should not be publicly posted in GitHub issue comments or PRs when it contains identifying or security-sensitive records.

## 7. Implementation and acceptance boundaries

This issue (#588) **defines and documents** the proposed logging policy; it does not claim to fix audit coverage, logging atomicity, user deletion, database constraints, or record immutability.

After approval, issue #447 can implement missing event coverage and standardise the sanitised event format. Approval events introduced in #606 should use the same rules and make bypasses distinguishable.

**Policy review acceptance:**

1. Required event categories and excluded data are explicitly documented.
2. The retention period is either approved or identified as an unresolved decision.
3. Append-only normal operations and restricted read/maintenance access are defined.
4. Existing limitations and migration/implementation dependencies are visible.
5. Stuart and Product Owner have reviewed and approved the policy before treating it as a committed standard.

## 8. Decisions for Stuart / Product Owner

1. **Retention:** approve 180 days, set another period or define separate periods for categories?
2. **Read access:** admin-only or include explicitly authorised supervisor read access?
3. **Data minimisation:** approve stable internal IDs and structured/sanitised details in place of emails/names for future events?
4. **Unauthenticated events:** how should login failures with no valid user ID be represented under the current required `user_id` schema?
5. **Deleted users:** how should historical audit events remain valid after user removal?
6. **Existing records:** should current email-containing `details` be reviewed as a separate maintenance task?
7. **Ownership:** who approves and runs retention disposal, preservation holds and access reviews?
